# 序章 0.2《把查表换成可学习的函数》· 讲义与追问实录

> 对应代码:`prologue/02_neural_bigram.py` | 状态:✅ 完成(2026-10-19)

## 一句话

把 0.1 的「数数表」换成**带参数的函数** `f(cur) = softmax(W[cur])`,用梯度下降训练——随机初始化的 W 自己走到了数数表的最优解。**会师,不是升级**:0.2 买到的是「可训练性」,不是新能力。

## 核心概念

- **表的两个死穴**:①不会学(换语料推倒重数);②长不大——真实数据实测覆盖率爆炸:

  | 前文宽度 N | 可能的上下文 | 实际出现 | 覆盖率 |
  |---|---|---|---|
  | 2 | 4,489 | 1,637 | 37% |
  | 4 | 2,015 万 | 8.3 万 | 0.4% |
  | 6 | 904 亿 | 65 万 | 0.0007% |
  | 8 | **406 万亿** | 181 万 | **4.5×10⁻⁹** |

- **W 为什么是 67×67**:输入 67 选 1,输出必须是 67 个概率(加和为 1);行 = 当前字符,列 = 下一个字符——与 `counts` 账本**同形状**(会师的形状基础);
- **one-hot @ W = W 的第 cur 行**(手算 3×3:`[0,1,0] @ W = 0×行0 + 1×行1 + 0×行2 = 行1`,"**1 选行,0 删行**")→ **查表本来就是一层线性层**;
- **softmax**:分数 → 概率。手算 `softmax([2,1,0]) = [0.665, 0.245, 0.090]`;减 max 防溢出(数值稳定版);
- **交叉熵 loss** = `-log p(正确字符)`;**梯度 = probs − onehot**——两行代码的反向传播,毫无魔法;
- **为什么参数不随前文爆炸**:表格把知识存在「每种上下文」上(上下文数量指数爆炸);网络把知识存在「字符含义 + 组合规则」上(字符数恒为 67)。0.3 方案:每字符 16 维含义向量(67×16)+ 拼接后 (48,67) 组合矩阵,**合计 4288 ≈ 0.2 的 4489,一个参数没多**。JS 类比:`map[entireContext]` vs `compose(embed(c1), embed(c2), embed(c3))`。

## 学员追问实录(金矿区)

1. **f(cur) 怎么理解?为什么 67×67?** → 见上「核心概念」;重点:形状由「67 进 67 出」的接口决定。
2. **67×67 不是没解决 3 字符问题吗?** → **完全正确**,教师确认:0.2 能力上就是 bigram,一分没涨。它证明的是「学习机器」能精确复现数数(2.50 vs 2.47),爆炸问题的解法在输入侧,0.3 才换。
3. **为什么前文加长参数不必爆炸?** → 知识的存放位置不同(上下文 vs 字符含义);406 万亿行的表 vs 4288 个参数的函数;没见过的上下文由字符含义**组合**出来(泛化 = 共享)。
4. **onehot @ W 为什么等于某一行?** → 手算迷你矩阵:one-hot 是「行选择器」,加权求和退化为选择。所以代码直接写 `W[cur_ids]`,数学同款还免乘法。
